# 已知问题与定位进展

## 2026-10-13 修复与双实例复测

外部 PR #2（英雄切换后的菜单重建）和 #3（服务器流送启动配置保护、修复安装）已合并至候选分支。安装器补充验证了连续 Repair 对原始 BOM、只读属性及卸载备份的保留。隔离副本实际运行中，两项流送值已均为 1；下述加入故障仍然出现，不能归因于流送配置为 0。

两份独立 UserDir、不同离线英雄在原版开始游戏后均有完整角色。客户端直连时，房主的本地控制器触发 `OnEndPlay(Destroyed)` 及 `OnDestroyed`，未观察到房主 Mod 的地图切换 EndPlay。其 Pawn、PlayerState、Camera 随后为空，触发多个原生空指针访问。仅保护相机读取不足以修复联机；保护后仍在游戏 RVA `0x30dea58` 崩溃。

随后捕获销毁调用链：`PreLogin (0x638f330) -> Actor.Destroy -> World.DestroyActor`。原生匹配函数 `0x63714a0` 对比网络 UniqueId，匹配后清理已有角色及控制器。两端共用 Steam 身份，触发了这条旧玩家替换路径；早先观察到队伍玩家标识相同，并不是这里使用的比较字段。

0.1.2 改为在原生 PreLogin 前拒绝与本地房主匹配的网络身份，不修改身份、不跳过不同身份的原生验证。实测同身份请求被拒绝，客户端返回菜单并显示原生错误 0015；房主的 Pawn、PlayerState、相机、GameState 与监听保持完整，鼠标点击移动成功。临时空指针保护与销毁追踪已移除。此项验证解决已复现的房主崩溃，并不证明不同账号的完整联机链路通过。

本机 `OutputDebugStringW` 存在每次约 10 秒的等待。测试启动器使用 `-LanDirectQuietDebug`，仅处理本进程的调试输出通知，原生文件日志保留；这改善测试启动速度，不代表握手、复制或存档已通过。

## 2026-10-12 本机双实例加入失败

已在两个独立游戏副本、独立 UserDir 和不同离线英雄下完成第一轮回环直连测试。房主在菜单及主世界监听 UDP 7777；加入端请求 `127.0.0.1:7777` 后进入带网络驱动的 Overworld，但未得到 GameState 或正常可控角色，随后房主发生读取空地址的访问冲突，故障位于游戏 EXE RVA `0x6268ba2`。

这项结果确认当前候选存在加入失败，不能向朋友宣称可用联机。两边同一 Steam 身份是否影响初始化尚待定位。测试 UserDir 配置被运行时改写/删除，流送 CVar 实际为 0，不能把本轮当作两项流送修正均有效的完整回归。准备方式及证据边界见 [本机双实例测试](LOCAL_DUAL_INSTANCE.md)。正式存档和配置哈希保持不变；转储和存档未上传。

### 已确认的流程差异

0.1.0 的主菜单开服和加入直接调用 OpenLevel，跳过原版“开始游戏”处理流程。该差异需要修正，但不等同于已经证明它导致地牢无限加载。

0.1.1 候选版改为：在主菜单检查离线玩家服务和可用的开始按钮，通过 CommonUI 原生点击处理器触发原版开始流程；等待角色生成、PlayerState 的角色关联非空并至少等待 5 秒，再发起 listen 或直连。切换后检查角色关联是否保持一致，失败则返回主菜单。请求状态仅保存在 GameInstance 内存中，进入菜单会清理，不写入英雄存档。

原版开始按钮处理器已在当前游戏构建运行并完成进入世界；只读检查确认角色关联非空。进入世界后也观察到 OnlinePlayerServiceImpl，因此不能仅凭这一类名断定绕过了离线初始化。主菜单离线检查与进世界后的角色关联检查分开处理。

### 2026-10-09 本机对照记录

本机另有尚未纳入公开安装包的原生桥接候选，使用 `EnableListenServer` 在既有地图开启监听，不执行第二次 `OpenLevel`：

- 主菜单开启 UDP 7777 后停留大厅，由用户点击原版“开始游戏”进入世界；角色关联检查通过，进入世界后重新建立监听。尚未验证第二台电脑加入大厅或世界。
- 一次矿车跨区域传送完成；随后进入上述地牢时，用户确认停在加载画面。这说明保留原版开始流程和避免第二次世界加载仍不足以解决问题。
- 卡住时，传送能力仍在等待 `AT_TeleportationGuard`，地图分块没有未完成加载或显隐请求；稍后传送任务结束。任务结束本身不能证明进入地牢成功。
- 开服状态下 1351 个地图分块全部加载；普通启动时只加载角色附近约 38 个。这个差异尚未被证明是故障原因。
- 普通启动后，用户确认同一入口的地图图标和现场入口均未出现。只读检查发现对应入口对象及所在分块仍存在，但 `Destination.IsActive=false`，目的地为空。尚不能断定是正常地牢选择差异，还是开服后错误启用了入口。
- 普通模式改测另一个有效入口后，用户确认成功进入地牢。只读检查同时记录到 `DeepDark_Anchor_Boss` 关卡已加载、传送能力不再活动，且世界没有网络监听。该结果尚未与开服模式的同一有效入口配对复测。
- 随后再次开服，用户改选另一个开放地牢，仍停在加载。此时主世界流送完成，但目标地牢没有创建动态流送关卡，传送的目标关卡就绪条件未通过。不能把入口轮换本身当作故障原因。
- 本机试验在启动时启用 `wp.Runtime.EnableServerStreaming=1` 和 `wp.Runtime.EnableServerStreamingOut=1`。两项设置一同修改，尚未拆分验证各自的必要性。配置和存档均有本地备份，这项变更尚未纳入公开安装器。
- 该组合生效后，用户确认成功进入一个开放地牢。记录显示 `DD_ANC_017` 动态地牢关卡已加载，传送源的主世界流送与目标关卡就绪条件均通过，随后传送任务结束；同时 UDP 7777 仍在监听。主世界仅加载附近约 46 个分块，流送策略中有 3 个流送源。

当前证据支持服务器流送设置是这次故障的主要原因：切为 listen server 后，默认的主世界全量加载方式没有完成地牢所依赖的按需流送链路，目标关卡未创建，原版传送检查持续等待。修正流送设置后，原版关卡加载与就绪检查自行完成，没有跳过检查或强行关闭加载界面。地牢轮换导致此前无法做同一入口对照，仍需更多入口验证。

以上是单台电脑运行记录，不代表多人联机、地牢过图或保存已经验证。
